What is this environment?

CareOtter is a vulnerable cardiac device ecosystem simulator for security testing and learning. It reproduces a realistic modern cardiac remote-monitoring deployment composed of two layers:

1. DAI/ICD Implant — a simulated cardiac implant (Implantable Cardioverter-Defibrillator) represented by a MAX30102 pulse-oximeter sensor connected via I2C to the bedside monitor. It generates continuous cardiac telemetry (BPM / SpO₂) and accepts therapeutic commands such as defibrillation simulation and threshold configuration.

2. Bedside Monitor / Home Monitor — a Raspberry Pi 3B+ running OpenWRT that acts as the clinical gateway. It reads vitals from the implant over I2C, exposes them via BLE for bedside/mobile review, streams them over HTTP to the hospital cloud, and provides device administration through a legacy binary protocol (IGP v4).

VulnZoo WWW interface — device management, loading/resetting the CareOtter simulator, and project administration.

CareOtter device interface — the bedside monitor and its vulnerable services (BLE, HTTP, IGP v4). This is where you perform penetration testing against a realistic medical IoT gateway.

Where to start?

You should initialize the CareOtter device first by clicking the "Load CareOtter" button. Then you can access the cloud_api/careotter folder on the VulnZoo repository and launch the Flask API server by executing "docker compose up --build -d". Finally, you should install the Android app on your phone and connect it to the same WiFi network as your PC to start interacting with the device.

"http://ip_cloud:5002/hint" will provide you with the first hints in order to know the initial configuration of the device and how to interact with it.

Lab prerequisites

  • WiFi — the attacker PC (running Docker) and the Android phone must be on the same WiFi network so the mobile app can reach the Cloud API.
  • Bluetooth — the phone must have Bluetooth enabled to pair with the BLE GATT server running on the Raspberry Pi.
  • Ethernet — a direct cable between Raspberry Pi and PC is required (PC static IP 192.168.2.2/24) for Pi-to-Cloud-API communication and all network attacks.

Device architecture

  • DAI/ICD Implant (MAX30102) — I2C-connected pulse-oximeter sensor simulating the cardiac implant. Provides BPM / SpO₂ telemetry and receives therapeutic commands.
  • Bedside Monitor (Raspberry Pi) — OpenWRT gateway that reads I2C data from the implant, runs BLE, HTTP, and IGP v4 services.
  • BLE — GATT services exposed by the bedside monitor for continuous heart rate and SpO₂ monitoring, interacting with mobile apps and wearables.
  • Cloud API — backend gateway (Flask) bridging the bedside monitor's IGP v4 admin protocol to REST, enabling remote monitoring and clinician dashboards.
  • Web interface — embedded dashboard with real-time cardiac telemetry, device status, and admin controls.
  • Mobile app — Android companion connecting via BLE to the bedside monitor or via WiFi to the cloud API.

Security training focus

CareOtter supports multiple security profiles via idempotent hooks that reconfigure the device without code changes.

  • Phase 1 — Secure. Baseline secure configuration with all protections enabled.
  • Phase 2 — Wireless. Relaxed BLE controls for wireless attack surface practice.
  • Phase 3 — Network. Weakened cloud and API protections for network attacks.
  • Phase 4 — Data. Reduced storage and logging protections for data extraction.

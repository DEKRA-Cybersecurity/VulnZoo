What is this environment?

OctoBot is a vulnerable industrial control system (ICS) simulator built around a real 4-DOF robot arm. It models a small industrial cell where a network attacker who exploits a web or protocol flaw ends up moving physical hardware. It is composed of three layers:

1. Robot arm + controller — a 4-servo arm (HU-M16 shield on an Arduino UNO) driven in real time by the Arduino. The Arduino plays the role of a real-time controller (a "PLC/microcontroller") and keeps its local joystick control as a manual fallback. It accepts remote Sx:angle commands over USB serial.

2. Field gateway — a Raspberry Pi 3B+ running OpenWRT that sits on top as the OT field gateway. It translates network protocols into the serial command bus and carries the entire OWASP IoT attack surface: a raw serial bus, MQTT, Modbus/TCP, an HMI/REST panel, and an unsigned OTA firmware-flash path.

3. Cloud controller — a Dockerized Flask service on the PC that hosts the operator web UI and REST API and acts as the Modbus/TCP master that drives the Pi.

The lab runs with or without the physical arm: when no Arduino is attached, the gateway simulates the serial line so every network path and vulnerability is still reproducible.

Where to start?

Click "Load OctoBot" to deploy the lab on the Raspberry Pi. The init hooks install dependencies, detect the arm (or fall back to simulation), and start the services on the Pi.

Then launch the cloud controller from the VulnZoo repository: cd cloud_api/octobot && docker compose up --build -d, then open http://localhost:5003 and log in with the single operator account (default operator / octobot) to reach the control panel.

You can also use the cloudctl.sh script to launch the cloud controller: ./cloudctl.sh start.

Detailed launch, service checks, and per-vulnerability reproduction live in the repo docs: docs/OctoBot/OctoBot.md (launch & verify) and docs/OctoBot/Vulns/ (OWASP IoT catalog).

Lab prerequisites

  • Ethernet — a direct cable between Raspberry Pi and PC (Pi 192.168.2.1, PC static 192.168.2.2/24) for the cloud-to-Pi Modbus/TCP link and all network attacks.
  • Docker — on the attacker PC, to run the cloud controller (:5003).
  • Robot arm (optional) — Arduino UNO + HU-M16 shield + 4 servos, connected to the Pi by USB. Without it the lab runs in simulation.
  • Servo power (with the arm) — an external 5 V / 2-3 A supply to the HU-M16 servo rail with a common GND across PSU, Arduino, and Pi. Do not power four moving servos from the USB rail.
  • Isolation — run on a dedicated, air-gapped LAN. This is deliberately vulnerable and physically moves hardware.

Device architecture

  • Arduino UNO — real-time servo controller, PWM to the arm, local joystick fallback, remote Sx:angle serial protocol at 115200.
  • Serial bus (:2000) — single owner of the Arduino serial line (or a simulator when no arm is present), exposed as an unauthenticated raw TCP gateway.
  • HMI / REST gateway (:8090) — Flask panel with /api/move, /api/claw, /admin, /logs, and the OTA /update endpoint.
  • Modbus/TCP (:502) — holding registers mapped to servo angles and commands, driven by the cloud master.
  • MQTT (:1883) — no-auth broker plus a bridge forwarding cell01/cmd to the serial bus.
  • Cloud controller (:5003) — Flask REST + web UI + Modbus/TCP master, the only surface the operator and app talk to.

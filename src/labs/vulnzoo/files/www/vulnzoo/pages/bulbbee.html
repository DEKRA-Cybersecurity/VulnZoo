What is this environment?

BulbBee is a vulnerable consumer smart-light simulator for security testing and learning. It reproduces a budget WiFi smart light: a Raspberry Pi 3B+ running OpenWRT drives an addressable WS2812 RGB LED ring. The controller is an Android app that drives the device over three planes: a BLE GATT server on the Pi (local, in range, as in CareOtter), an outbound cloud tunnel (the device dials a broker, so the app controls it remotely over the Internet), and a local AES-CCM channel on the LAN. The app signs in to a cloud account and picks the channel automatically, BLE when the bulb is nearby and the cloud otherwise. A local HTTP control API on :8082 is a secondary surface to set power, brightness, color and named scenes.

BulbBee is the VulnZoo reference for a Cyber Resilience Act default-category product: a device that falls in no vertical of Annex III or Annex IV and therefore follows the lightest conformity route, self-assessment under Module A with a self-declared EU Declaration of Conformity. The lab is framed as the sample a CRA assessor receives, and you play the assessor testing a self-declared product against the baseline.

VulnZoo WWW interface: device management, loading and resetting the BulbBee simulator, and project administration.

BulbBee device interface: the BLE GATT control and onboarding channel (the app's local path), the outbound cloud tunnel that carries remote control (app to cloud to device), the local AES-CCM plane on :6668, and the HTTP control API on :8082 for diagnostics.

NOTE: Loading the BulbBee lab will restart the Raspberry Pi. Check after a few seconds if the device is responding.

Where to start?

Initialize the device first by clicking the "Load BulbBee" button. The lab runs headless in simulation with no ring attached, so you can start immediately.

Then drive the light over the control API:

  • curl http://192.168.2.1:8082/health - liveness
  • curl http://192.168.2.1:8082/state - current power / brightness / color / scene
  • curl -X POST http://192.168.2.1:8082/scene -d '{"scene":"rainbow"}' - animate a rainbow

Lab prerequisites

  • Ethernet: a direct cable between Raspberry Pi and PC (PC static IP 192.168.2.2/24), the Pi is at 192.168.2.1.
  • Bluetooth: the controller (an Android phone or a BLE-capable host) needs Bluetooth enabled to reach the BLE GATT control server on the Pi (implemented, BULB-A2).
  • WS2812 ring (optional): DIN to Pi GPIO10 (pin 19), 5V to pin 2/4, GND to pin 6. SPI must be enabled (dtparam=spi=on). Without a ring the lab runs in simulation.

Device architecture

  • BLE GATT control server (app channel): the local controller path, the app connects over BLE to set power, brightness, color and scene and to onboard the device over WiFi (implemented, BULB-A2, modeled on CareOtter).
  • Lighting service (Raspberry Pi): OpenWRT service driving the WS2812 ring over SPI, with a simulation fallback, and the secondary HTTP control API on :8082.
  • WS2812 ring: addressable RGB LEDs on the SPI0 MOSI line (GPIO10), scenes solid / off / rainbow / breathe.
  • Local AES-CCM plane: a scannable TCP channel on :6668 for low-latency local control, encrypted with a static firmware key. It is an analysis and attack surface, not the app's default path.
  • Cloud API: a Flask backend on :5004 with an MQTT broker. The device holds an outbound tunnel and the API relays account commands to it, so remote control (app to cloud to device) works end to end (implemented, BULB-R1..R6): account-device binding, single-use claim tokens, a device state uplink and a device-liveness signal.
  • Mobile app: the Android companion. Login-first with a persisted cloud session, automatic BLE-proximity-then-Cloud transport with failover on a dropped link, plus offline and link-device states (implemented).

Security training focus

BulbBee teaches the CRA baseline that applies to every product with digital elements, mapped to OWASP IoT Top 10, OWASP API and Mobile Top 10, and ETSI EN 303 645. The vulnerabilities are implemented across the BLE, cloud and app surfaces and documented.

  • Onboarding: open setup AP and hardcoded pairing credentials.
  • Control: unauthenticated local API, cleartext replayable command channel.
  • Update: unsigned over-the-air update of the lighting service.
  • Data and resilience: plaintext secrets, insecure defaults, scene-payload denial of service.
  • Cloud API: broken object-level authorization (any account controls any bulb) and broken authentication (the alg:none forge and a weak JWT secret), which the command relay turns into remote physical control of any user's bulb.
  • Mobile app: a hardcoded factory pairing PIN extractable from the APK, and WiFi and cloud credentials stored in plaintext.
